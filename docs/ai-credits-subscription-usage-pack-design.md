# Anybox AI 额度、月度订阅与加油包设计方案

> 文档状态：讨论稿  
> 更新日期：2026-07-12  
> 适用范围：Anybox Managed AI Provider 服务端、桌面端及支付接入  
> 相关文档：[Anybox 全球 MoR 申请与落地计划](./mor-application-plan.md)

## 1. 背景与结论

Anybox Managed AI Provider 当前面向用户展示人民币余额，并按模型调用成本扣减余额。随着产品准备增加“月度订阅”和“一次性加油包”，继续把用户权益描述为现金余额会产生以下问题：

- 用户容易将其理解为可提现、可转让或可退款的电子钱包余额。
- 每次使用都显示“扣钱”，会放大用户的消费压力。
- 上游模型价格、汇率和利润率变化会直接暴露给用户。
- 订阅赠送、促销赠送、补偿额度和加油包难以放进统一权益模型。
- 海外支付平台可能将现金等值余额识别为 stored value、礼品卡或第三方 API 转售。

本方案确定以下产品与技术原则：

> **面向用户统一展示 AI 额度；底层继续按人民币精确核算成本。**

- 人民币负责订单支付、退款、收入、成本和毛利核算。
- AI 额度负责用户权益发放、使用、过期和回收。
- AI 额度只能用于 Anybox Managed AI Provider，不可提现、不可转让、不可兑换现金、不可作为通用支付工具。
- 用户购买的是 Anybox 托管 AI 服务权益，不是第三方模型账户、API Key 或第三方余额。
- AI 额度与人民币之间不存在用户可执行的反向兑换关系。

## 2. 目标与非目标

### 2.1 目标

1. 用同一套额度账户支持月度订阅、加油包、活动赠送、人工补偿和退款回收。
2. 对用户提供清晰、可解释的剩余额度和消费明细。
3. 在模型价格变化时允许服务端调整计费规则，而不直接修改用户已有额度。
4. 保留准确的 Token、上游成本、订单收入和毛利数据。
5. 保证并发调用、流式响应、Webhook 重试和退款场景下的账务一致性。
6. 避免将产品设计成现金钱包或可交易的虚拟货币。

### 2.2 非目标

- 不提供额度提现、转账、交易或赠送功能。
- 不允许额度购买第三方商品或服务。
- 不向用户提供上游模型厂商的账户、API Key 或充值码。
- 不要求所有模型永久维持固定人民币换算比例。
- 本文不确定最终套餐价格、额度数量和支付渠道费率，这些需要单独评审。

## 3. 用户侧产品模型

### 3.1 统一名称

中文统一使用：

- `AI 额度`
- `月度订阅额度`
- `加油包额度`
- `赠送额度`
- `额度明细`

英文建议使用：

- `AI usage units` 或 `AI usage allowance`
- `Monthly usage allowance`
- `Additional AI Usage Pack`

不建议继续使用以下用户侧表述：

- 余额充值
- 钱包余额
- 储值余额
- 可用金额
- 账户资金

### 3.2 用户可见信息

账户页至少展示：

- 当前可用 AI 额度总数。
- 本月订阅额度的剩余数量和重置时间。
- 加油包额度的剩余数量和有效期。
- 最近的额度发放、消耗、过期、退款和补偿记录。
- 基于典型任务计算的粗略可用次数，仅作为估算。

示例：

```text
可用 AI 额度：8,600
本月订阅额度：6,000，将于 8 月 1 日重置
加油包额度：2,600，有效期至 2027 年 7 月 12 日

本次任务消耗：32 AI 额度
```

不要直接向普通用户展示 Token 数、上游 API 原价、内部人民币成本或利润率。高级用量明细可以展示模型、输入/输出规模、工具类型和额度消耗，但仍以 AI 额度作为最终用户计量单位。

### 3.3 订阅不应只有额度

月度订阅除了每月额度，还可以包含以下权益：

- 高级模型访问权限。
- 更高的并发数或速率限制。
- 更大的上下文窗口。
- 自动化、云端任务或其他高级功能。
- 更高的文件、存储或同步限制。

这样可以避免订阅退化为纯粹的预付充值，并让套餐价值不只由单位额度价格决定。

## 4. 商品设计

### 4.1 月度订阅

每个订阅套餐建议定义：

- 套餐 ID 和版本。
- 月费及币种。
- 每个账期发放的 AI 额度。
- 可访问的模型和功能权限。
- 并发、速率和其他服务限制。
- 生效时间、续费时间和取消时间。

推荐规则：

- 订阅额度在每个成功付款账期开始时发放。
- 月度订阅额度默认不结转，下个账期重新发放。
- 取消订阅后，本期权益保留到已付款账期结束。
- 付款失败进入短暂宽限期；宽限期结束仍未支付，则停止发放新额度并降级权益。
- 有效月度订阅可立即升级到同币种且价格严格更高的套餐。抵扣按当前周期套餐原价和未使用时长向下取整计算；支付成功后结束旧周期，从付款时间重新开始一个完整高价套餐月，并将周额度重置为 100%。
- 已付款的下月续费不被覆盖，保持原套餐和金额并顺延到新套餐月结束后生效。若过期订单迟付或来源周期已经变化，实付款幂等转入预付余额，不覆盖当前订阅。
- 降级默认下个账期生效，避免回收本期已承诺权益。
- 同一个付款账期只能发放一次额度，必须由幂等键保证。

当前上线约束（2026-07-13）：

- 手动“续费一个月”和“下个账期切换”入口暂时下线，Web 与桌面客户端均不得创建续费订单。
- 无订阅记录的用户仍可完成首次订阅；有效订阅只开放同币种、月付且价格严格更高套餐的立即升级。
- 订阅到期或失效后不再展示付款入口，等待微信支付和支付宝自动扣款能力完成后再恢复续费。
- 历史已付款的未来账期和历史待支付续费订单继续兼容展示、状态查询与取消，但不得通过更换支付方式重建续费订单。

### 4.2 加油包

加油包是一次性购买的额外服务用量，不改变用户订阅等级。

每个加油包建议定义：

- 商品 ID 和版本。
- 售价及币种。
- 发放的 AI 额度。
- 有效期。
- 可购买的用户范围和数量限制。
- 是否仅对订阅用户开放。

推荐规则：

- 支付成功后一次性发放。
- 只能由购买账户消费。
- 不可提现、转让或兑换现金。
- 建议设置清晰且较长的有效期，例如购买后 12 个月；具体期限需结合支付平台、消费者保护和退款政策确认。
- 如果 Merchant of Record 不批准一次性用量包，则通过功能开关关闭，只上线月度订阅。

### 4.3 免费与赠送额度

系统应支持免费试用、运营赠送和客服补偿，但必须记录来源、原因、操作人和有效期。

建议区分：

- `trial`：注册或首次使用试用额度。
- `promotion`：活动赠送额度。
- `compensation`：故障或客服补偿额度。
- `manual_adjustment`：经过授权的人工调整。

赠送额度不应伪装成现金，不产生提现或退款价值。

## 5. 额度消耗规则

### 5.1 扣除顺序

每笔额度发放形成一个独立批次（grant/lot）。消费时优先扣除最早过期的额度，避免用户因系统顺序不合理而损失权益。

推荐排序：

1. 按 `expires_at` 从早到晚扣除。
2. 到期时间相同时，优先扣订阅额度，再扣加油包额度，再扣赠送额度。
3. 永不过期额度最后扣除。

具体顺序必须由服务端统一实现，客户端不得自行决定。

### 5.2 不允许透支

- 默认不允许额度账户出现负数。
- 开始请求前进行额度检查和预占。
- 额度不足时返回明确的业务错误，引导用户升级订阅或购买加油包。
- 服务端故障、退款追缴等特殊情况不应通过直接制造负余额解决，应进入独立的风险或人工处理状态。

### 5.3 流式请求的预占与结算

LLM 调用在开始时通常无法获得最终 Token 数和成本，因此需要两阶段处理：

```text
额度检查 → 预占额度 → 调用上游模型 → 获取实际用量 → 正式结算 → 释放剩余预占
```

建议：

1. 根据模型、上下文规模、最大输出和工具类型计算预占额度。
2. 在一个短事务内原子地创建 reservation 并减少可用额度。
3. 上游返回实际 usage 后，按请求开始时锁定的计费规则计算实际额度。
4. 实际消耗低于预占时释放差额；高于预占时在允许范围内补扣。
5. 请求失败时根据失败阶段决定全额释放、收取已发生用量，或进入待核对状态。
6. 对缺少 usage 的上游响应使用明确的估算规则，并标记 `estimated=true`。
7. reservation 必须有过期回收机制，防止进程崩溃后额度永久冻结。

### 5.4 工具与非文本能力

除文本 Token 外，计费规则应支持：

- 图片生成和编辑。
- 视频生成。
- 语音识别和语音合成。
- 搜索、浏览器、沙箱或其他付费工具调用。
- 云端自动化任务和长时间 Agent 运行。

不同能力可以使用不同计量维度，但最终都换算为整数 AI 额度。

## 6. 额度与人民币成本的关系

### 6.1 双账本原则

用户权益账与财务成本账必须分离：

```text
用户权益账：本次消耗 32 AI 额度
内部成本账：输入 Token、输出 Token、工具调用、actual_cost_cny
订单财务账：用户支付金额、税费、渠道手续费、退款金额
```

不要只保存额度而丢失实际成本，也不要用人民币成本字段直接充当用户余额。

### 6.2 换算规则可版本化

额度消耗由服务端的计费规则计算，例如：

```text
credits = input_usage × input_rate
        + output_usage × output_rate
        + tool_usage × tool_rate
        + fixed_request_fee
```

具体规则需要满足：

- 使用整数额度，避免浮点累计误差。
- 每个计费规则有版本号和生效时间。
- 请求开始时锁定规则版本，不能因请求期间发布新价格而改变。
- 用量记录保存完整的计费规则快照或可追溯版本。
- 允许不同模型、能力、地区或套餐采用不同倍率。
- 调价只影响新请求，不批量重算历史流水或用户已有额度。

购买页可以给出“约可完成多少次典型任务”的估算，但不要承诺固定任务次数。若使用“100 额度约等于 ¥1 的基础使用价值”作为初期认知锚点，也不应形成可兑换或永久固定汇率承诺。

### 6.3 成本精度

- 支付金额使用币种最小单位保存，例如人民币分、美元美分。
- 上游成本可使用更高精度的十进制定点数或微货币单位保存。
- AI 额度使用整数类型保存，推荐 `BIGINT`。
- 禁止使用二进制浮点数作为账务最终值。

## 7. 服务端领域模型

以下是建议的逻辑模型，具体表名可适配现有 anyboxProvider 架构。

### 7.1 `credit_accounts`

额度账户投影，用于快速查询，不作为唯一审计来源。

关键字段：

- `id`
- `user_id`
- `available_credits`
- `reserved_credits`
- `status`
- `version`：乐观锁版本
- `created_at`
- `updated_at`

### 7.2 `credit_grants`

每次发放形成一个额度批次，用于处理来源、有效期和消费顺序。

关键字段：

- `id`
- `account_id`
- `source_type`：subscription、usage_pack、trial、promotion、compensation、manual
- `source_id`：账期、订单、活动或工单 ID
- `granted_credits`
- `remaining_credits`
- `effective_at`
- `expires_at`
- `status`：active、exhausted、expired、revoked
- `idempotency_key`
- `metadata`
- `created_at`

### 7.3 `credit_ledger_entries`

不可变额度流水，是额度账的审计依据。

建议类型：

- `grant`
- `reserve`
- `release`
- `consume`
- `expire`
- `revoke`
- `refund_reversal`
- `manual_adjustment`

关键字段：

- `id`
- `account_id`
- `grant_id`
- `usage_id` 或 `reservation_id`
- `entry_type`
- `credits_delta`
- `balance_after`
- `business_reference_type`
- `business_reference_id`
- `idempotency_key`
- `reason`
- `created_by`
- `created_at`

已入账流水不得更新或删除。纠错通过新增反向流水完成。

### 7.4 `credit_reservations`

记录进行中的额度预占。

关键字段：

- `id`
- `account_id`
- `request_id`
- `reserved_credits`
- `settled_credits`
- `status`：active、settled、released、expired、review_required
- `pricing_rule_version`
- `expires_at`
- `created_at`
- `settled_at`

### 7.5 `credit_consumption_allocations`

一笔消费可能从多个额度批次扣除，因此需要保存消费与 grant 的分摊关系。

关键字段：

- `id`
- `usage_id`
- `grant_id`
- `consumed_credits`
- `created_at`

### 7.6 `usage_records`

记录实际模型或工具使用情况。

关键字段：

- `id`
- `user_id`
- `request_id`
- `provider_id`
- `model_id`
- `capability`
- `input_units`
- `output_units`
- `tool_units`
- `credits_charged`
- `actual_cost_amount`
- `actual_cost_currency`
- `pricing_rule_version`
- `estimated`
- `status`
- `started_at`
- `completed_at`

### 7.7 `pricing_rules`

保存可版本化的模型和能力计费规则。

关键字段：

- `id`
- `version`
- `provider_id`
- `model_id` 或能力范围
- `calculation_rule`
- `effective_from`
- `effective_until`
- `status`
- `created_at`

### 7.8 订单与订阅

建议保留独立模型：

- `products`：订阅套餐和加油包商品定义。
- `prices`：按渠道、币种和地区定义价格版本。
- `orders`：一次性购买和支付状态。
- `subscriptions`：用户订阅生命周期。
- `subscription_periods`：每个账期及其发放状态。
- `payment_events`：支付平台原始 Webhook 事件与处理状态。
- `refunds`：退款请求、结果和权益回收状态。
- `entitlements`：套餐附带的非额度功能权限。

订单、订阅、额度发放和额度流水之间必须通过稳定的业务 ID 关联，但不能合并成同一张“余额表”。

## 8. 核心业务流程

### 8.1 订阅首次付款或自动续费（自动扣款接入后启用）

```text
接收付款成功 Webhook
→ 验证签名并保存原始事件
→ 通过 payment_event_id 幂等去重
→ 创建或更新订阅账期
→ 按 product/version 创建 credit_grant
→ 创建 grant 流水
→ 开通或延长功能权益
→ 返回成功并异步通知用户
```

Webhook 重放不能重复发放额度。

### 8.2 购买加油包

```text
创建订单
→ 支付平台结账
→ 接收支付成功 Webhook
→ 幂等确认订单
→ 创建 usage_pack credit_grant
→ 创建 grant 流水
→ 更新额度账户投影
```

客户端支付成功页面不能作为发放依据，额度只能由服务端确认的支付事件触发。

### 8.3 模型调用

```text
鉴权与套餐权限检查
→ 读取当前计费规则
→ 估算并原子预占额度
→ 调用模型或工具
→ 记录真实 usage 和成本
→ 结算额度并写入分摊记录
→ 更新账户投影
→ 返回用户可见的本次额度消耗
```

### 8.4 额度过期

- 定时任务将到期且仍有余额的 grant 标记为 expired。
- 为未使用部分创建 `expire` 流水。
- 原子更新账户可用额度投影。
- 过期任务必须可重复运行且保持幂等。
- 在到期前通过产品通知提醒用户，避免无感损失。

### 8.5 退款与撤销付款

推荐技术策略：

1. 退款事件先锁定对应订单或账期，避免继续消费相关权益。
2. 回收该订单或账期尚未使用的额度，并创建反向流水。
3. 已使用部分按照公开退款政策决定是否允许退款、部分退款或转人工审核。
4. 不删除历史 grant、消费或成本记录。
5. 拒付和欺诈退款可冻结账户并进入风险处理，不应悄悄制造负余额。
6. 功能权益的回收应与额度回收分开执行并记录状态。

最终退款规则必须与用户协议、退款政策及支付平台要求一致。

## 9. API 建议

以下只定义领域边界，不要求沿用具体路径。

### 9.1 用户接口

```http
GET  /api/billing/credits/summary
GET  /api/billing/credits/grants
GET  /api/billing/credits/ledger
GET  /api/billing/usage
GET  /api/billing/products
GET  /api/billing/subscription
POST /api/billing/checkout/subscription
POST /api/billing/checkout/usage-pack
POST /api/billing/subscription/cancel
```

当前 Anybox Provider 的立即升级流程使用两阶段接口：

```http
POST /api/subscription/upgrade-quotes
POST /api/subscription/upgrade-orders
```

报价有效 5 分钟，创建支付订单时必须锁定并复核来源周期、目标套餐、金额和已付续费状态；变化时返回 `upgrade_quote_changed`，由客户端重新报价并要求用户再次确认。

`credits/summary` 建议返回：

```json
{
  "availableCredits": 8600,
  "reservedCredits": 120,
  "subscription": {
    "remainingCredits": 6000,
    "renewsAt": "2026-08-01T00:00:00Z"
  },
  "usagePacks": {
    "remainingCredits": 2600,
    "nearestExpiresAt": "2027-07-12T00:00:00Z"
  }
}
```

### 9.2 内部接口或领域服务

建议提供以下原子能力：

- `grantCredits(command)`
- `reserveCredits(command)`
- `settleReservation(command)`
- `releaseReservation(command)`
- `expireGrant(command)`
- `revokeGrant(command)`
- `getCreditSummary(userID)`
- `quoteUsage(command)`
- `recordActualCost(command)`

所有写操作必须要求 `idempotencyKey` 和业务引用 ID。

### 9.3 错误码

至少定义：

- `INSUFFICIENT_CREDITS`
- `SUBSCRIPTION_REQUIRED`
- `MODEL_NOT_INCLUDED`
- `CREDIT_ACCOUNT_FROZEN`
- `RESERVATION_EXPIRED`
- `PRICING_RULE_NOT_FOUND`
- `PAYMENT_NOT_CONFIRMED`
- `DUPLICATE_BILLING_EVENT`

错误响应应告诉客户端下一步可执行动作，例如购买加油包、升级订阅或重试，而不是暴露上游成本细节。

## 10. 一致性、安全与审计要求

### 10.1 事务与并发

- grant 消费、reservation 和账户投影更新必须位于数据库事务中。
- 使用行锁、乐观锁或原子 SQL 防止并发超扣。
- 不依赖 Redis 作为唯一账务真相；缓存只能作为投影或加速层。
- 账务数据库失败时宁可拒绝调用，也不能先调用上游再丢失消费记录。

### 10.2 幂等

以下场景必须幂等：

- 支付 Webhook。
- 订阅账期额度发放。
- 加油包发放。
- 模型请求结算。
- reservation 释放和过期。
- 退款权益回收。
- 定时过期任务。

业务唯一键应由数据库唯一约束保障，不能只靠应用层查询。

### 10.3 审计

- 流水不可变。
- 人工调整必须记录操作人、原因、工单或审批引用。
- 支付平台原始事件需保留可核对版本，并对敏感字段脱敏。
- 每日执行账户投影与流水汇总对账。
- 每日执行订单收入、额度发放、实际成本和支付平台结算对账。

### 10.4 权限

- 普通客服只能查看账务摘要和提交补偿申请。
- 人工发放、回收和冻结需要独立后台权限。
- 高额度调整建议双人审批或至少产生告警。
- 用户身份、支付账户和额度账户的绑定变更必须审计。

## 11. 从人民币余额迁移到 AI 额度

迁移前必须先确认当前“余额”的法律和产品性质：

- 如果它只是 Anybox 内部计算出的服务可用量，且不可提现，可按明确规则迁移为 AI 额度。
- 如果它是用户真实充值形成且承诺可退款的现金余额，不能只改显示名称；需要保留历史现金权益、退款责任和独立账务处理。

### 11.1 推荐迁移步骤

1. 冻结迁移时点和旧余额快照。
2. 为每个用户生成迁移批次，保存旧余额、币种、换算规则和新额度。
3. 创建 `migration` 类型的 credit grant 和不可变流水。
4. 保留旧充值订单和人民币流水，不覆盖、不删除。
5. 新版本客户端只展示 AI 额度，旧版本接口进入兼容期。
6. 对账确认“迁移前总权益 = 迁移后总额度所代表的服务权益”。
7. 向用户说明名称、使用方式、有效期和退款权利是否发生变化。
8. 灰度发布并准备回滚显示层；账务迁移本身不得依赖删除数据回滚。

### 11.2 兼容接口

兼容期可以暂时返回：

```json
{
  "credits": 8600,
  "legacyBalanceDeprecated": true
}
```

不建议同时长期展示“¥86.00”和“8,600 额度”，否则用户仍会把额度理解为可兑换现金余额。

## 12. 运营与财务指标

服务端应支持按用户、套餐、模型、渠道和时间范围统计：

- 额度发放量、消耗量、过期量和回收量。
- 订阅额度使用率。
- 加油包购买率和复购率。
- 免费额度转付费率。
- 每个套餐的收入、上游成本、支付费率和毛利。
- 每个模型或能力的平均额度消耗和实际成本。
- 额度不足导致的请求拒绝率。
- reservation 超时率、估算结算率和对账差异。
- 退款率、拒付率和异常额度调整量。

计费规则上线前应使用历史 usage 数据回放，验证用户可理解性和目标毛利，避免只根据单次简单对话定价。

## 13. 分阶段实施建议

### 阶段一：建立额度内核

- 新增 credit account、grant、ledger、reservation 和 usage 成本记录。
- 将现有人民币余额扣费改为内部成本记录与额度扣费并行。
- 完成幂等、并发防超扣和每日对账。
- 后台可查看人民币成本，但用户端仍可暂时保持旧显示用于灰度验证。

### 阶段二：切换用户表达

- 客户端将“余额”统一替换为“AI 额度”。
- 上线额度摘要、额度明细和单次任务消耗。
- 完成旧余额迁移和兼容接口。
- 更新用户协议、退款政策、定价页和帮助文档。

### 阶段三：上线月度订阅

- 接入订阅商品、账期、Webhook、取消和失败重试。
- 每个成功账期幂等发放月度额度和功能权益。
- 先完成 Sandbox 的支付、续费、取消、退款和重复 Webhook 测试。

### 阶段四：上线加油包

- 在支付平台书面允许后启用一次性用量包。
- 实现有效期、退款回收、购买限制和用户提醒。
- 使用功能开关按支付渠道或地区独立开放。

## 14. 服务端评审需要确定的问题

以下项目不应在实现中静默假设，需要产品、服务端、财务和支付合规共同确认：

1. 首发套餐数量、价格和每月额度分别是多少？
2. 免费用户是否允许购买加油包，还是必须先订阅？
3. 月度额度是否完全不结转？
4. 加油包有效期是 12 个月、其他期限还是按渠道区分？
5. 用户同时持有多个 grant 时，最终扣除优先级是否采用“最早过期优先”？
6. 升级立即生效、降级下周期生效是否符合支付平台能力？
7. 支付失败的宽限期和权益限制是什么？
8. 哪些错误场景需要收取已发生的模型用量？
9. 部分使用后的加油包是否允许部分退款？
10. 旧人民币余额属于服务用量还是可退款现金权益？迁移时是否保持原有效期？
11. 国内微信/支付宝与海外 MoR 是否使用同一商品和额度规则？
12. 额度消耗规则由静态配置、数据库后台还是版本化发布系统管理？
13. 实际成本核算使用人民币、美元还是同时保存原币与折算币？汇率快照从哪里获取？
14. 用户侧是否显示单次消耗，还是仅在用量明细中显示？
15. 是否需要为团队账户预留共享额度账户，但暂不开放转账？

## 15. MVP 验收标准

满足以下条件后，额度系统才适合承载真实付费：

- [ ] 用户侧不再把服务权益描述为现金钱包或可用金额。
- [ ] 订阅、加油包、赠送和补偿均可形成独立 grant。
- [ ] 每一笔额度变化均有不可变流水和业务来源。
- [ ] 100 个并发请求不会导致负余额或重复扣费。
- [ ] 流式请求支持预占、结算、释放和超时回收。
- [ ] 重复 Webhook 不会重复发放权益。
- [ ] 重复结算请求不会重复扣除额度。
- [ ] 每笔模型调用可追溯到额度消耗、计费规则版本和实际人民币成本。
- [ ] 模型调价不会改写历史流水或用户已有额度。
- [ ] 退款、拒付、过期和人工补偿均有可审计流程。
- [ ] 能完成额度账户投影与流水的自动对账。
- [ ] 能完成订单收入、退款、上游成本和毛利核算。
- [ ] 已通过支付成功、续费、失败重试、取消、退款和异常中断的端到端测试。
- [ ] 用户协议、退款政策、定价页和支付平台商品描述与实际规则一致。

## 16. 最终建议

Anybox 应将“人民币余额”从用户权益模型中移除，改为不可提现、不可转让、只能用于 Anybox 托管服务的 AI 额度。服务端仍需保留比当前更完整的人民币成本和订单财务记录，但这两套账的职责不同：

> **人民币负责支付与财务核算，AI 额度负责用户权益与使用消耗。**

实现时应优先建立不可变额度流水、分批次 grant、预占与结算、计费规则版本化和支付 Webhook 幂等。月度订阅在此基础上按账期发放额度；加油包在支付平台允许后作为额外用量批次发放。这样可以在保持用户体验稳定的同时，为模型调价、套餐调整、促销补偿和全球支付接入留下足够空间。
