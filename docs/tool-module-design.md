# Anybox 工具模块设计说明

> 更新日期：2026-08-09  
> 适合读者：第一次接触 Anybox 工具系统的产品、设计、开发和测试人员。  
> 文档定位：解释当前系统“为什么这样设计”和“各层如何配合”。工具参数与完整清单请看[官网工具文档](../packages/site/src/docs/content/tools.md)，严格协议请看 [ToolCall v3](./tool-call-v3.md) 与 [Tool Module V2 ADR](./tool-module-v2-architecture-decision.md)。

## 1. 先用一句话理解

可以把 Agent 想成一个会思考的工作人员：

- **Tool（工具）**是一件具体器具，例如读文件、执行命令、创建待办。
- **Tool Module（工具模块）**是一个工具箱，例如“文件读写”“Shell”“Planner”。
- **Provider（工具来源）**说明工具箱从哪里来，例如 Anybox 内置、MCP、插件或项目自定义代码。
- **Skill**更像操作手册，告诉 Agent 什么时候、按什么步骤使用工具。
- **Permission（权限）**是门锁，决定某一次具体操作能否真的执行。

最重要的一条边界是：

> 模块被加载，只代表 Agent 现在能看见其中的工具；不代表这些工具已经获得执行许可。

这条边界让 Anybox 可以同时做到三件事：能力多、上下文不臃肿、危险操作仍然受控。

## 2. 为什么不能把所有工具一次性都交给模型

最直接的实现，是把所有工具名称、说明和参数都放进每一次模型请求。但工具越来越多以后，会出现几个问题：

1. **占用上下文。** 即使用户只想改一个文件，模型也要先读完 Planner、MCP、图片生成等大量无关说明。
2. **增加选错工具的概率。** 名称相近、来源不同的工具越多，模型越容易混淆。
3. **启动成本变高。** 某些能力需要连接服务或初始化运行时，没有必要在每轮对话开始时全部启动。
4. **边界变得含糊。** 工具从哪里来、属于哪项能力、能存在多久，都容易混在一个大列表里。
5. **设置难以理解。** 用户看到几十个散落的开关，却不知道它们共同解决什么问题。

因此 Anybox 在“具体工具”上面增加了 Tool Module。模块不是为了多包一层代码，而是为了统一回答四个问题：

- 这些工具属于哪项能力？
- 它们从哪里来？
- 什么时候应该让模型看见？
- 这次加载可以持续多久？

## 3. 五个容易混淆的概念

| 概念 | 它负责什么 | 它不负责什么 |
| --- | --- | --- |
| Tool | 参数格式、具体执行、结果格式和风险属性 | 安装、分发和产品分组 |
| Tool Module | 能力分组、发现方式、激活方式和生命周期 | 某次调用是否获准执行 |
| Provider | 工具从哪里加载、通过什么方式连接 | 判断用户现在是否需要这项能力 |
| Plugin | 安装、版本和 Skill、MCP、Connector 等能力的分发 | 自动等同于一个模块或自动取得权限 |
| Skill | 使用方法、工作流和参考资料 | 注册可执行代码或绕过权限 |

模块与 Provider 必须分开理解。比如一个 Gmail 插件可以通过 MCP 提供工具：

- Provider 回答“这些工具由哪个 MCP server 提供”；
- Module 回答“这些工具在产品上属于哪项能力，以及何时暴露给 Agent”。

这样，即使未来同一项能力换了连接方式，工具的产品归属和激活语义也不必跟着重做。

## 4. 当前有哪些加载方式

Anybox 当前把模块分成“常驻”和“按需”两类。这里的“常驻”是指进入运行时目录，并不表示绕过全局开关、Agent 策略或权限检查。

### 4.1 常驻模块

常见的内置能力包括：

| 模块 | 解决的问题 |
| --- | --- |
| `workspace.file-io` | 读取、修改、补丁和查看工作区文件 |
| `workspace.file-search` | 列目录、按路径或内容搜索文件 |
| `workspace.shell` | 在受管理的 Shell 中执行命令和操作后台进程 |
| `workflow.tasks` | 跟踪当前 Agent 执行中的任务、依赖和进度 |
| `agent.multiagent` | 委派并管理边界清晰的子 Agent 工作 |
| `runtime.progressive-disclosure` | 按需发现 Tool、Skill、MCP 资源和工作区运行时 |
| `runtime.programmatic-orchestration` | 组合或并行执行适合编排的工具调用 |
| `runtime.python` | 在当前会话的持久 IPython 环境中运行代码；本地工作区可用且默认关闭 |
| `agent.metacognition` | 查看和回到较早的会话检查点 |
| `workspace.lsp` | 通过语言服务器理解代码符号 |
| `network.web` | 获取公开网页和网络资源 |
| `media.visual-generation` | 使用已配置的模型生成图像 |
| `interaction.human` | 向用户提出结构化问题并等待回复 |

具体工具会随操作系统和工作区变化。例如 Windows、macOS 与 SSH 工作区暴露的 Shell 工具并不相同；SSH 工作区也不会加载只适用于本机的 IPython 和 LSP 工具。

### 4.2 按需模块

在 Agent 对话运行时，按需模块平时只保留很轻的目录信息，不加载完整工具定义，也不初始化 execution。当前代表是 `planner.core`。桌面端工具页另有一条只读检查路径，可以临时读取定义和 Schema 供用户查看，但这不会激活模块或把工具交给模型。

它有两种激活方式：

1. Agent 发现缺少能力后，调用通用工具搜索；命中的模块从**同一用户轮次的下一次模型调用**开始可见。
2. 用户通过 `@计划`、`/计划` 或对应入口明确选择；模块从这轮的第一次模型调用起就可见。

`planner.core` 的激活范围是当前用户轮次。下一条普通用户消息开始时，它会自动恢复为未加载状态。这样，一次“帮我安排明天的待办”不会让后续所有普通对话永久携带 Planner 的整套工具说明。

### 4.3 MCP 与项目自定义工具

- 已配置或被本轮明确选择的 MCP Provider 可以直接提供工具。
- 未直接暴露的 MCP 工具可以按单个工具被搜索和发现，以兼容现有 MCP 行为。
- 项目运行时注册的自定义工具归入 `custom.project`，随当前项目提供。

原生按需模块采用“失败时保持隐藏”的策略。工具搜索不可用时，`planner.core` 不会为了兜底而整包暴露；用户仍可通过合法的显式入口加载它。部分历史 MCP 延迟工具保留了搜索不可用时直接暴露的兼容行为，这个兼容规则不会套用到原生按需模块。

## 5. 一轮对话里，工具是怎样进入模型的

可以把运行时理解为连续经过四道门：

```text
工具来源
  └─ 这项工具是否真实存在、属于哪个模块？
       ↓
模块目录
  └─ 该模块是常驻、已配置、搜索命中，还是仍应隐藏？
       ↓
本轮过滤
  └─ 全局开关、Agent 策略、模型能力和只读会话是否允许它出现？
       ↓
模型工具集
  └─ 只把这一轮真正可见的工具定义交给模型
```

对应到当前实现，一次解析大致是：

1. Registry 汇总内置、MCP 和项目自定义工具，并检查 ID、别名和模型可见名称不能冲突。
2. Module Catalog 为每项工具补齐模块归属和 Provider 来源，同时加入尚未加载的原生模块目录。
3. Resolver 合并项目配置、本轮显式选择和本轮工具搜索记录，得到模块的 `direct`、`deferred` 或 `hidden` 状态。
4. Resolver 再应用全局工具开关、Agent 允许/拒绝名单、模型输入能力要求和只读会话限制。
5. 只有最终可见的工具才会初始化 execution，并被包装成模型能够调用的工具集合（ToolSet）。

这套顺序有两个有意的设计：

- **先决定是否需要，再初始化。** 未激活的原生模块不会只是“藏住 Schema”，而是真的不创建工具 execution。
- **每一轮重新解析。** Runtime 不把某次发现误当成永久配置，重试和同轮续跑可以恢复发现结果，下一轮则自然失效。

## 6. 用 Planner 走一遍完整流程

假设用户说：“找出我今天没完成的待办，再安排一个两小时空档。”

```text
用户消息
  ↓
第一次模型调用：只有核心工具和通用工具搜索，没有 planner_*
  ↓
模型搜索“待办、排期”能力
  ↓
本地目录命中 planner.core，并把发现结果记在当前轮工具轨迹中
  ↓
同一轮的下一次模型调用：加载并显示 planner_* 工具
  ↓
模型调用读取待办、查找空闲时间等具体工具
  ↓
每个调用单独经过参数校验、权限判断、执行和结果记录
  ↓
模型整理结果并回复用户
  ↓
下一条普通用户消息开始：planner.core 不再自动保持激活
```

如果用户一开始就带上 `@计划`，流程会跳过“搜索”这一步，但不会跳过后面的权限判断。

这里也没有一个隐藏的“小模型”先替用户判断意图。普通文本直接交给主模型；主模型要么使用现有工具，要么明确调用工具搜索。这样可以避免多一次模型请求，也让“为什么加载了某项能力”留在可检查的工具轨迹里。

## 7. 工具被看见以后，为什么还不能直接执行

“可见性”和“可执行性”是两套独立判断：

| 层级 | 回答的问题 |
| --- | --- |
| 模块激活 | 这轮是否需要把该能力交给模型？ |
| 全局工具选择 | 用户是否在桌面端整体启用了这个内置工具？ |
| Agent 策略 | 当前 Agent 是否被允许使用它？ |
| 会话策略 | 当前会话是否只允许只读工具？ |
| 模型要求 | 当前模型是否具备工具需要的输入能力，例如图像输入？ |
| 调用级权限 | 对这一次参数、路径、命令和风险，应该允许、询问还是拒绝？ |
| 工具守卫 | 参数是否合法、工作区和运行条件是否满足？ |

所以桌面端工具页显示“已启用”，只表示该工具可以进入候选集合。真正调用时，仍可能因为路径越界、高风险命令、只读会话或用户拒绝而停止。

调用级权限不是只看“工具名字危险不危险”。执行框架会把工具声明的能力、实际参数、目标路径、工作目录以及工具给出的风险意图一起交给 Permission 层。必要时，UI 会显示将要运行的命令、路径或正文，让用户针对这一次调用作决定。

## 8. 为什么所有工具都经过同一个执行外壳

每个工具只需要声明自己的业务部分，公共规则由 `Tool.define()` 和 execution 层统一处理。

一项工具通常包含两部分：

- **静态信息：**稳定 ID、标题、别名、模块来源、默认开关、并发属性、只读/破坏性标记、模型要求和结果大小上限。
- **运行时实现：**参数 Schema、执行函数，以及可选的前置校验、授权守卫、风险评估、审批说明和模型输出转换。

统一外壳负责：

1. 按 Schema 校验模型传入的参数。
2. 检查运行前提和工具自身的授权边界。
3. 计算这次调用的权限决策，必要时等待用户审批。
4. 提供会话、消息、工作区、中断信号和模型信息等一致上下文。
5. 把字符串或结构化返回值规范成统一结果。
6. 处理过大的输出和内嵌附件。
7. 把稳定的来源、结果和状态交给消息流、模型与 UI。

这样做的价值不是少写几行代码，而是避免每个工具用自己的方式解释“校验失败”“用户拒绝”“执行报错”或“输出太大”。

## 9. ToolCall v3：状态、结果和下一步是三回事

当前工具调用采用 ToolCall v3。它刻意把三个问题拆开：

1. **生命周期走到哪里？** `pending`、`waiting_approval`、`running`、`settled`。
2. **最后得到了什么结果？** 正常返回、被阻止、被拒绝、取消、超时或技术故障。
3. **当前模型轮次接下来怎么走？** 继续推理、等待用户、结束、重启循环、失败或取消。

这能解决一个很常见的误解：

> 工具正常运行并返回“没有找到结果”，不是系统执行失败。

几个例子：

| 场景 | ToolCall 结果 | 含义 |
| --- | --- | --- |
| Shell 正常启动并以非零码退出 | `returned / negative` | 命令给出了有效的否定结果，不是传输故障 |
| IPython 运行了代码，但用户代码抛出异常 | `returned / negative` | 运行环境正常返回了业务结果 |
| 参数不符合 Schema | `blocked` | 执行前被安全地挡住，可让模型修正参数 |
| 用户拒绝高风险操作 | `denied` | 审批结果明确拒绝 |
| MCP 连接中断 | `failed` | 没有获得有效工具结果，属于技术故障 |
| 工具结果被截断 | `returned / partial` | 已有有效结果，但内容不完整 |

结果还会记录副作用是否可能或已经发生，以及自动重试是否安全。UI 不需要从错误文字、退出码或颜色反推状态；桌面端、移动端、历史回放和运行时共用同一份结构化快照。

## 10. 大结果为什么要落盘

工具结果可能是一小段文字，也可能是几万行日志、JSON、图片或其他附件。如果把大结果完整塞进数据库消息和模型上下文，会拖慢渲染，也会挤掉真正重要的对话内容。

因此执行层会检查工具自己的结果上限和系统上限：

- 小结果直接返回。
- 超大文本、超大结构化结果或内嵌二进制数据会保存到当前会话的受管理 artifact 目录。
- 模型收到简短预览和可读取的本地路径，需要时再用文件工具读取完整内容。
- metadata 中保留清单、大小、哈希和持久化位置，方便 UI、诊断和清理。

这相当于把“整箱资料”存进档案室，只在桌面上放摘要和索引。

## 11. 桌面端“工具”页面的边界

工具页面是目录和全局可用性管理界面，不是权限审批中心。

- 常驻内置模块可以整组或逐项修改；模块开关最终仍保存为逐工具选择，避免模块重组时破坏已有配置。
- 按需模块可以只读查看工具说明、风险属性和输入 Schema；浏览它们不会激活模块，也不会改变后续对话。
- 页面显示模块归属、Provider、激活方式、作用域和工具能力，帮助用户理解“它从哪里来、什么时候出现”。
- MCP 的连接、认证和健康状态仍由“连接”管理，不由内置工具页面接管。
- 权限审批仍发生在具体调用上；全局启用不等于自动批准。

## 12. 新增或修改工具时的设计检查

新增工具时，建议按下面的顺序思考：

1. **先选能力边界。** 它属于已有模块，还是确实需要一个新的模块？不要因为实现文件不同就拆模块。
2. **再选 Provider。** 它来自 Anybox 内置、原生领域服务、MCP、插件运行时还是项目自定义注册？
3. **定义稳定契约。** 选择不会随 UI 文案变化的工具 ID，给出严格但易修正的参数 Schema。
4. **声明真实能力。** 正确填写只读、破坏性、并发、Shell 依赖、模型输入要求和默认开关。
5. **区分三类拦截。** 参数/前提用 validation，工具自身资源边界用 authorization，面向用户的风险判断用 permission intent。
6. **返回结构化事实。** 业务未达成用 negative，内容不完整用 partial，只有没有获得有效协议结果时才用 failed。
7. **显式控制模型轮次。** 需要等待用户或结束当前轮时返回明确 control，不依赖工具名称或结果文案猜测。
8. **验证失败策略。** 核心能力缺失应尽早报错；可选模块加载失败应保持隐藏且可诊断，不能出现半注册状态。
9. **补齐测试。** 至少覆盖名称冲突、可见性、只读过滤、审批、取消、超时、结果语义、来源追踪和大输出。

## 13. 当前设计刻意不做什么

- 不在主模型前增加隐藏的意图分类模型。
- 不把“模块被加载”当作“工具已授权”。
- 不把 Plugin、Module、Provider、Skill 混成同一个概念。
- 不把一次当前轮加载写成永久项目配置。
- 不允许客户端提交任意 loader 路径、代码或自报 Schema 来注册原生模块。
- 不在可选模块加载失败时暴露一部分工具，形成不可预测的半可用状态。

这些限制看起来保守，但它们保证了系统扩展以后仍然可解释、可审计、可恢复。

## 15. 维护约定

以下变化发生时，应同步检查本文：

- 新增 Module 激活模式、作用域或发现粒度。
- 新增一类 Provider，或改变 MCP / Plugin / custom tool 的归属方式。
- 改变 Resolver 的可见性过滤顺序。
- 改变 Permission、ToolCall outcome 或 turn control 的含义。
- 改变按需模块的生命周期，或新增第二个原生按需模块。
- 改变工具页面对常驻和按需模块的管理边界。
