# 构建 Web 应用

构建 Web 应用（`build-web-apps`）是一组面向前端开发的 Skills。它帮助 Agent 从产品目标和视觉方向出发，完成界面实现、浏览器测试、React 优化，并在需要时应用 shadcn/ui、Stripe 和 Supabase/Postgres 的专项实践。

> 这个插件提供工作方法和工程规范，不是网站托管服务，也不会自动连接支付账号、数据库或生产环境。实际的文件写入、命令、浏览器、部署和外部账号访问仍由当前项目可用的工具与 Connector 决定，并遵循各自的审批规则。

## 什么时候使用

适合启用这个插件的任务包括：

- 从零构建落地页、产品网站、Dashboard、内部工具或交互式前端。
- 在现有 React 或 Next.js 项目中增加一段完整用户流程。
- 根据截图、设计稿或品牌方向重做界面，并保持响应式表现。
- 排查页面空白、运行时报错、交互失效、控制台异常和移动端布局问题。
- 优化 React 渲染、数据请求、包体积与用户感知性能。
- 正确组合 shadcn/ui 组件，或为 Stripe、Supabase/Postgres 集成制定安全的实现方案。

如果只是修改一行文案或修复一个很小的样式问题，Agent 可以沿用现有设计系统直接处理，不必重新探索完整视觉方向。

## 安装并为项目启用

1. 从 Anybox 左侧导航打开「插件」。
2. 搜索 `构建 Web 应用` 或 `build-web-apps`，查看其中包含的 Skills，然后点击「安装」。
3. 在当前项目顶部菜单的插件选择器中启用它。
4. 打开目标代码仓库，并告诉 Agent 运行方式、目标页面、技术栈和不可改变的边界。
5. 如需真实浏览器验收，同时启用 Chrome 插件并启动本地开发服务器。

插件不带独立的 MCP Server 或 Connector 设置。仅安装插件不会获得浏览器、Stripe、Supabase、部署平台或其他账号的访问权限。

## 包含的 Skills

| Skill | 主要作用 |
| --- | --- |
| `frontend-app-builder` | 从需求、视觉方向和设计系统推进到可运行的前端实现 |
| `frontend-testing-debugging` | 在浏览器中进行页面识别、控制台检查、交互验证与响应式 QA |
| `react-best-practices` | 减少请求瀑布、无效重渲染和包体积，改善 React/Next.js 性能 |
| shadcn/ui 最佳实践 | 查找、安装、组合和定制真实的 shadcn/ui 组件 |
| Stripe 最佳实践 | 设计支付集成、Webhook 和服务端边界时采用更安全的模式 |
| Supabase/Postgres 最佳实践 | 改善数据库结构、查询、索引、连接和行级安全策略 |

这些 Skills 会根据任务自动提供相关指导，并不表示每次任务都会同时使用全部技术。一个不涉及支付的纯前端页面不需要 Stripe；一个已有组件库的项目也不应为了使用插件而强行迁移到 shadcn/ui。

## 推荐工作流

### 1. 先定义结果

说明页面服务谁、核心动作是什么、必须展示哪些内容，以及完成标准。例如：

> 在当前 Vite + React 项目中实现一个插件文档首页。保留现有路由和品牌色；桌面端需要左侧导航，窄屏改为选择器。完成后用 Chrome 验证首页、搜索和两种视口，不要部署。

### 2. 检查现有项目

Agent 会先读取框架、脚本、组件、样式变量和已有页面，尽量复用项目的设计语言。对于全新且视觉要求较高的界面，在图像生成能力可用时，它可能先生成或比较视觉方向；如果你已有设计稿，或只想做小修复，可以直接要求沿用现有系统。

### 3. 建立清晰的视觉系统

先确定字体层级、颜色、间距、边框、圆角、阴影和响应式规则，再组合页面。避免用大量彼此不一致的局部样式“拼”出界面。

### 4. 实现可运行版本

Agent 在当前仓库内修改代码，保留既有架构和用户改动，并运行项目已有的格式检查、类型检查或测试。需要安装依赖、执行迁移或改变构建配置时，应说明影响范围。

### 5. 用真实页面验收

开发服务器可用时，优先使用 Chrome 检查真实页面，而不是只根据源码推断。至少确认：

- 打开的是正确页面，并且不是空白或框架错误覆盖层。
- 控制台没有与本次修改有关的错误。
- 目标按钮、表单、导航或筛选能够完成预期交互。
- 桌面和窄屏视口都没有明显溢出、遮挡或不可达内容。
- 最终截图与原始目标或设计参考一致。

### 6. 明确交付边界

完成时应列出改动、验证结果和仍需人工配置的项目。除非你明确要求并授权，构建完成不等于部署、发布、提交支付配置或修改生产数据库。

## 推荐的任务写法

- “在这个仓库中构建一个响应式产品首页，复用现有 token 和组件；先给出页面结构，再实现并用 Chrome 验收。”
- “根据这张截图重做设置页，只修改渲染层，不改变 IPC 和数据模型。”
- “排查移动端菜单点击后不展开的问题，先复现和解释原因，再修复并验证。”
- “评审这个 React 页面，重点检查请求瀑布、包体积和不必要的重渲染；不要改代码。”
- “为现有结账流程设计 Stripe 集成方案，先列出服务端、Webhook 和幂等边界，不要创建真实产品或收款。”
- “检查这些 Supabase 查询和 RLS 策略，给出索引与权限建议；不要连接或修改生产数据库。”

同时写清技术栈、目标路由、参考设计、允许修改的目录、验证命令以及是否允许安装依赖或访问外部服务。

## 浏览器测试与 Chrome

`frontend-testing-debugging` 会在浏览器能力可用时优先验证真实页面。Chrome 插件适合读取当前页面、检查控制台和页面结构、执行交互并留存截图，尤其适合本地开发站点和需要现有登录状态的后台。

如果 Chrome 不可用，Agent 可以根据项目已有测试工具采用其他验证方式；但“构建成功”只能证明产物能够编译，不能替代对布局和交互的实际检查。

## 支付、数据库与外部服务边界

- Stripe Skill 是实现指导，不会自动获得 Stripe 账号或密钥，也不会自行创建产品、价格或收款。
- Supabase/Postgres Skill 是数据库设计与性能指导，不会自动连接或修改任何数据库。
- 账号凭据应进入 Anybox 的安全配置或对应平台的推荐密钥管理机制，不要写入源码、Markdown、截图或提交记录。
- 数据库迁移、生产写入、真实付款、部署和发布都属于独立动作，应明确目标环境并在执行前单独确认。
- 浏览器中的登录状态仅在启用 Chrome 且你允许使用相应标签页时可用；安装本插件不会读取浏览器会话。

## 常见问题

### 安装后没有新的工具

这是预期行为。构建 Web 应用是 Skill 集合，不声明自己的 MCP Server 或 Connector。它会改进 Agent 处理前端任务的流程，但实际执行仍使用项目已有的文件、命令、图像和浏览器能力。

### Agent 想重新设计，但我只要小修复

在请求中写明“沿用现有设计系统，不探索新视觉方向”，并限制允许修改的组件或文件。小范围修复不需要完整的概念设计阶段。

### 页面编译通过但显示不正确

启动开发服务器并启用 Chrome，让 Agent 打开确切路由，检查页面身份、控制台、截图和目标交互。也要验证至少一个窄屏视口。

### 提到 Stripe 或 Supabase，但没有账号访问

插件只提供最佳实践。需要实际操作时，应另行配置对应凭据和可用工具，并明确开发、测试或生产环境。在这之前，Agent 应停留在代码与方案层面。

### 现有项目已经使用另一套组件库

继续使用现有组件库。shadcn/ui 指南是可选能力，不是迁移要求；一致性通常比引入第二套组件系统更重要。

## 与其他插件配合

- 使用 Chrome 对本地页面、已登录后台和响应式界面进行真实 QA。
- 使用 Cinema 构建影片项目后，可用本插件制作素材审核台或展示页。
- 只有必须操作原生桌面软件时，才使用 Windows 电脑控制。
