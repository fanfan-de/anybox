# 使用场景

Anybox 的工作流保持一致：选择项目、创建会话、说明目标、检查执行过程并确认结果。变化的是项目上下文、允许使用的能力和最终交付物。

## 这页的用途

下面的场景用于帮助你选择一个大小合适的首个任务。示例不是能力承诺；实际结果取决于项目内容、模型、工具、权限和已连接的扩展。

优先选择你能独立验证的任务，并在开始时说明哪些内容可以读取、哪些内容可以修改。

## 软件开发

适合从一个明确的问题或可验证的改动开始：

- 解释目录结构和关键模块之间的关系。
- 定位错误日志对应的代码路径。
- 为已有行为补充测试。
- 在保持现有接口的前提下重构局部模块。
- 汇总变更并准备提交或 PR 摘要。

示例请求：

> 阅读当前项目的入口和测试配置，先说明结构，不要修改文件。最后列出三个最值得优先检查的风险。

确认方案后，再单独授权写入和测试步骤。这样可以把“理解项目”和“修改项目”分成两个易于检查的阶段。

## 研究与办公

当资料已经位于工作区中时，可以让 Agent：

- 按主题整理会议记录或调研材料。
- 比较多个方案的目标、成本、风险和未决问题。
- 从表格或文本资料中提取可核对的结论。
- 把零散记录整理为提纲、方案或行动清单。
- 为后续沟通准备摘要，但由你决定是否发送或发布。

示例请求：

> 阅读 research 目录中的资料，按“已确认事实、存在分歧、缺失信息、建议下一步”整理一份 Markdown 摘要。不要访问目录外的文件。

如果任务涉及外部服务，先确认连接会发送哪些数据以及是否需要登录凭据。

## 内容与创作

Anybox 可以围绕已有项目材料推进创作：

- 依据产品事实整理网页文案或文档草稿。
- 把大纲扩写为文章、脚本或演示结构。
- 比较多个表达方向，并说明各自取舍。
- 根据反馈继续修订同一份项目文件。
- 为复杂交付拆出可检查的阶段和清单。

示例请求：

> 根据当前目录中的产品说明，写一版克制、事实导向的中文介绍。不要补写资料中没有的功能，并把待确认的说法单独列出。

生成内容可能流畅但仍可能包含错误。发布前应逐项核对名称、数字、链接、平台状态和能力边界。

## 推荐步骤

1. 选择一个结果可以被测试、比较或逐条核对的任务。
2. 把所需资料放在清晰的项目目录中。
3. 说明目标、读写边界、输出格式和完成标准。
4. 先让 Agent 阅读并提出计划，再决定是否执行写入。
5. 检查工具调用、文件变更、错误和最终回复。
6. 运行适合当前项目的验证，或人工核对关键事实。
7. 把有效流程整理为 Skill，供后续同类任务复用。

## 成功表现

- 输出直接对应最初目标，没有把相邻想法当成已授权工作。
- 重要结论能追溯到项目文件、工具结果或明确的用户输入。
- 发生修改时，变更范围与任务边界一致。
- 未能验证的内容被明确标记，而不是被写成事实。
- 最终结果包含可执行的下一步或可核对的交付物。

## 数据与权限影响

本地文件、终端命令和外部连接属于不同能力边界。只读任务也可能把选中的内容发送给当前模型；远程 MCP 工具还可能把参数发送给对应服务。

使用真实业务资料前，先移除不必要的密钥、个人信息和受限制数据。对删除、覆盖、发布或外部写入操作保持更严格的检查。

## 常见问题

### 任务应该写多详细？

至少说明目标、允许访问的范围、是否可以修改、预期格式和完成标准。复杂任务可以先要求计划。

### 一个会话可以处理很多不相关任务吗？

可以继续对话，但按目标拆分会话通常更容易保持上下文清晰，也更便于回看结果。

### Agent 没有按预期执行怎么办？

先检查模型是否可用、资料是否在当前项目、所需工具是否启用，以及权限请求是否仍在等待处理。
